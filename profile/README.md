<p>把一条线路当商品看参数，比听描述靠谱。同样写着「住宅 IP」，ASN、归属地精度、复用率、并发上限这几个参数不同，用起来的差别能有一倍。这篇按说明书的形式列参数：出口七个字段、环境四个字段、计费三个口径，最后给一张可以直接填空的配置单。预算紧的时候，先看懂参数再决定买哪种，比反复换服务商省事。</p>
<h2>一、出口参数：七个字段看懂一条线</h2>
<p>拿到线路信息，先对着七个字段过一遍。缺哪个就问服务商要，问不到的基本可以不用考虑。</p>
<h3>字段一至三：地址、归属、运营商</h3>
<p>地址格式（IPv4 单地址还是 /29 小段）、归属地（国家-省州-城市三级）、运营商与 ASN。归属地精度要求到城市，只写到国家的信息没有参考价值，因为跨城登录本身就会引起注意。</p>
<h3>字段四至五：类型与复用率</h3>
<p>类型分住宅、移动、机房。复用率指同一地址被多少个客户同时使用，独享为 1，共享池常见 3 到 20，超过 20 就接近公共出口了。复用率一般不写在明面上，靠问和靠测：连续三天查同一地址的会话特征是否变化。</p>
<h3>字段六至七：并发与切换方式</h3>
<p>并发上限指这条线同时允许几个连接，住宅线路通常 3 到 10，低于 3 的多端登录会互相挤掉。切换方式分固定、可换、自动切备用，长期跑任务要选后两者之一。</p>

<h2>二、环境参数：浏览器与系统要一起改</h2>
<p>出口定了，环境参数得跟着出口走，不能反过来。四个字段：时区、语言、UA 平台、WebRTC 策略。</p>
<h3>时区与语言必须同源</h3>
<p>出口在美西就设 America/Los_Angeles，语言 en-US；出口在伦敦就设 Europe/London，语言 en-GB。用 JS 执行 Intl.DateTimeFormat().resolvedOptions().timeZone 验证，改完刷新页面再看一次，有些客户端会缓存旧值。</p>
<h3>WebRTC 与 UA 的两个细节</h3>
<p>WebRTC 可能绕过代理暴露本地地址，指纹浏览器里通常有「替换为代理出口」的选项，记得打开。UA 不要手动乱改版本号，用真实浏览器版本最自然，改了版本却留着旧字体列表，反而是个矛盾点。</p>
<h2>三、计费参数：三个口径怎么比</h2>
<p>价格不能直接比数字，得先对齐口径。同一家服务商的三种口径，单位成本可能差三倍，但适用场景完全不同。</p>

<h3>预算紧的时候怎么配</h3>
<p>思路是「固定加弹性」：主力号包月，波动部分用按小时或按流量补。比如十个号里六个长期在线走包月，四个按小时计费，只在白天开。这样既保证主力环境稳定，又不用为闲置时间付钱。</p>
<h3>别忽略的计费细节</h3>
<p>三处容易吃亏：换线是否另计费、闲置是否仍计费、超并发如何计费。三条都问清楚，写在订单备注里。尤其是「闲置计费」，包月按条通常是照付的，按小时才是真停。</p>

<h2>四、把参数填成一张配置单</h2>
<p>参数看懂了，落成一张单子才有用。下面的结构可以照抄，一个号一行，交接时直接给下一个人。</p>
<h3>配置单要写什么</h3>
<p>账号标识、出口地址、归属城市、ASN、环境文件名、时区、语言、并发上限、计费档、开通日期、续费日期。十一项，一行填完，三十秒。填写人签名比字段更重要，出了问题知道找谁。</p>
<h3>参数变了怎么办</h3>
<p>只增行不覆盖。每次换线、改时区、调并发，都新加一行并写变更原因。这张单子同时也是复盘材料：某段时间异常变多，翻一下那几天改了什么，往往一眼能看出来。</p>
<h3>每月对账看三列</h3>
<p>月底拉一次表，只看三列：实际在线天数、计费档位、异常次数。在线天数低于十五天的号，下月切按小时；异常次数高于三次的号，先查环境再谈换线。对账十分钟，能省下不少冤枉钱。</p>
<h2>常见问答</h2>
<h3>并发上限 3 条，三个人同时登会怎样？</h3>
<p>答：第三条之后的新连接会被拒绝或挤掉已有连接，表现是有人突然掉线。三个人的话，要么升并发，要么错开登录时段，别硬顶。</p>
<h3>归属地只写到国家能买吗？</h3>
<p>答：可以，但要接受不确定性。城市不明的线路，登录地可能落在你不熟悉的区域，订阅扣费时更容易被判异地。预算允许还是选能指定城市的。</p>
<h3>按流量计费会不会超支？</h3>
<p>答：纯文本对话消耗很小，一个号一天通常几十 MB；上传文档或图片才会明显上涨。设一个月度上限提醒，超过就切包月。</p>
<h3>参数都对，为什么还是被要求验证？</h3>
<p>答：参数只覆盖静态部分，行为节奏是另一回事。新号第一天高频操作、短时间多次登录退出，都会触发验证，跟参数没关系。</p>
